راهنمای کامل API داخلی و صف ماژول ssbhesabfa

نسخه مستندات: 2.3.20

این API برای ماژول‌های دیگر PrestaShop است تا بدون نگهداری نام کاربری، رمز یا API Key حسابفا، درخواست‌های خود را از طریق ssbhesabfa اجرا یا صف کنند.
پیش‌نیازهافراخوانی مستقیمفراخوانی صفورودی‌هاخروجی‌هاRetry و UUIDمثال‌هامتدها

۱. پیش‌نیازها و سیاست اتصال

  • ماژول ssbhesabfa باید نصب و فعال باشد.
  • متد در فهرست مجاز کلاس HesabfaApi وجود داشته باشد.
  • برای اجرای مستقیم، اتصال حسابفا باید برقرار باشد.
  • در معماری صف، ایجاد job نباید به اتصال لحظه‌ای وابسته باشد؛ بررسی اتصال باید در زمان اجرای job انجام شود.
LIVE_MODE: در حالت synchronous پیش از تماس API بررسی شود. در حالت asynchronous رویداد ابتدا ذخیره شود؛ اگر هنگام اجرا اتصال برقرار نبود، job باید با کد HESABFA_NOT_CONNECTED در retry_wait بماند.

۲. فراخوانی مستقیم

$module = Module::getInstanceByName('ssbhesabfa');
if (!$module || !$module->active) {
    throw new Exception('ssbhesabfa is not available.');
}

$result = $module->callInternalApi(
    'invoiceGet',
    array(12345, 0),
    array(
        'requester' => 'mycustommodule',
        'object_type' => 'Order',
        'object_id' => 1001,
        'queue' => false,
        'log_request' => true,
    )
);

۳. فراخوانی صف

$queued = $module->enqueueInternalApiRequest(
    'invoiceSave',
    array($invoicePayload),
    'mycustommodule',
    'Order',
    (int) $idOrder
);

خروجی اولیه فقط پذیرش در صف را نشان می‌دهد؛ به معنای موفقیت در حسابفا نیست.

  "success": true,
  "request_id": 321,
  "status": "pending"
}

۶. وضعیت صف، Retry و requestUniqueId

وضعیتمعنیاقدام
pendingمنتظر اولین اجراتوسط cron یا اجرای دستی پردازش می‌شود.
runningدر حال اجرانباید هم‌زمان دوباره اجرا شود.
retry_waitخطای موقت یا نتیجه نامشخصبا همان UUID و backoff مجدداً اجرا می‌شود.
needs_attentionخطای داده، تنظیمات یا دسترسیابتدا علت اصلاح شود؛ عملیات جدید UUID تازه می‌گیرد.
duplicate_checkUUID تکراری یا قدیمی‌تر از ۲۴ ساعتنتیجه قبلی در حسابفا بررسی شود.
doneعملیات موفقفقط تاریخچه؛ نباید همان payload قدیمی دوباره اجرا شود.
deadتعداد تلاش‌ها تمام شدهبررسی دستی و در صورت نیاز عملیات جدید.
یک retry فنی با payload یکسان باید همان UUID را نگه دارد. تغییر payload یا شروع عملیات منطقی جدید باید UUID تازه تولید کند.

۹. امنیت و نکات اجرایی

  • اطلاعات ورود حسابفا را در ماژول فراخواننده ذخیره نکنید.
  • درخواست‌های مالی و نوشتنی را ترجیحاً از صف عبور دهید.
  • موفقیت پذیرش در صف، موفقیت عملیات حسابفا نیست.
  • برای متدهای Save/Delete/Set، مدیریت UUID به ماژول مرکزی واگذار شود.
  • در لاگ عمومی payload شامل رمز، token یا API key چاپ نشود.

مستندات رسمی endpointها: Hesabfa API Documentation

Queue connection and completed-record behavior

Queued requests are accepted independently of the current live connection after API credentials have been configured. Connection status is checked immediately before execution. If Hesabfa is offline, the request remains in retry_wait without consuming an attempt. A done record is historical and has no Run again action; create a new request with current input when a new operation is required. Completed records also reject forged direct-run or requeue submissions at the repository/service layer.

شماره فاکتور حسابفا ممکن است در سال مالی جدید دوباره از ۱ آغاز شود. به همین دلیل کد حسابفا برای mappingهای order و returnOrder به‌تنهایی یکتا نیست. یکتایی اصلی mapping بر اساس نوع موجودیت، شناسه پرستاشاپ و شناسه ترکیب حفظ می‌شود. برای کالا و مشتری، کنترل تکراری بودن کد حسابفا همچنان فعال است.

رفتار خطای پرداخت و سند کارمزد

در نسخه 2.3.10 شکست ثبت پرداخت فاکتور یا سند درآمد کارمزد دیگر موفق تلقی نمی‌شود. متد setOrderPayment() مقدار false برمی‌گرداند و صف بر اساس پاسخ واقعی حسابفا وضعیت retry_wait یا needs_attention را انتخاب می‌کند.

Placeholderهای توضیحات پرداخت و اسناد حسابداری

قالب‌های توضیحات پرداخت و سند درآمد کارمزد از placeholderهای زیر پشتیبانی می‌کنند:

  • {order_id}: شناسه عددی سفارش در پرستاشاپ.
  • {order_reference}: مرجع سفارش در پرستاشاپ.
  • {invoice_number}: شماره فاکتور حسابفا.
  • {transaction_number}: شماره تراکنش درگاه یا پرداخت.
  • {customer_charge_percent}: درصد مبلغ افزوده‌شده به پرداخت مشتری.
  • {fee_percent}: درصد کارمزد درگاه پرداخت.
  • {income_percent}: درصد سود خالص سند نسبت به مبلغ پایه فاکتور.
پرداخت سفارش {order_reference} - فاکتور {invoice_number} - تراکنش {transaction_number} - نرخ افزوده مشتری {customer_charge_percent}% - کارمزد درگاه {fee_percent}% - سود خالص {income_percent}%

در پرداخت‌های خودکار، مقدار {order_reference} از مرجع همان سفارش خوانده می‌شود. در پرداخت دستی، این مقدار از فیلد اختیاری «مرجع سفارش» در فرم پرداخت دستی گرفته می‌شود و در صورت خالی بودن، با مقدار خالی جایگزین خواهد شد.

اقلام فاکتور در Webhook

ممکن است فاکتور حسابفا شامل کالاها یا خدماتی باشد که به محصولی در فروشگاه آنلاین متصل نیستند. اگر قلم فاکتور Tag معتبر مربوط به فروشگاه نداشته باشد، ماژول آن را با ثبت لاگ نادیده می‌گیرد و پردازش تغییر فاکتور و checkpoint ادامه پیدا می‌کند. اگر قلم دارای Tag فروشگاه باشد اما mapping، محصول یا ترکیب متناظر آن خراب یا حذف شده باشد، پردازش همچنان خطا محسوب می‌شود تا اتصال معیوب به‌صورت واقعی اصلاح شود.

پوشش ترجمه فارسی

در نسخه 2.3.15 تمام عبارت‌های قابل‌ترجمه فعلی در فایل‌های PHP و قالب‌های Smarty دارای ترجمه متناظر در translations/fa.php هستند.

Webhook store tag filtering

Invoice items, products and contacts received from Hesabfa are applied only when their Tag contains a valid positive id_product or id_customer. Objects that are not connected to the online store are ignored and do not block the webhook checkpoint.

Item code mismatch guard

During Hesabfa-to-PrestaShop price and stock synchronization, if the item code received from Hesabfa does not match the existing local mapping, the module logs the mismatch, keeps the mapping unchanged, and skips applying price or stock for that item. The webhook checkpoint continues. Resolve the mismatch through the manual review workflow before changing the mapping.

فیلتر و صفحه‌بندی صف‌ها در نسخه 2.3.16

صف اصلی حسابفا و صف درخواست‌های API داخلی دارای فیلترهای مستقل برای وضعیت، نوع عملیات، موجودیت، کد خطا، بازه تاریخ و کلیدواژه هستند. هر صفحه حداکثر ۵۰ رکورد نمایش می‌دهد و شماره صفحات به‌صورت فشرده مانند 1 2 3 … 50 51 52 نمایش داده می‌شود.

تلاش مجدد خودکار و توقف دستی صف در نسخه 2.3.17

خطاهای موقت در وضعیت retry_wait قرار می‌گیرند و پس از رسیدن زمان next_run_at توسط کرون به‌صورت خودکار دوباره اجرا می‌شوند. وضعیت‌های needs_attention، duplicate_check و dead خودکار اجرا نمی‌شوند.

برای رکوردهای pending، retry_wait، needs_attention و duplicate_check دکمه «علامت‌گذاری به‌عنوان مرده» اضافه شده است. این عملیات اجرای خودکار رکورد را متوقف می‌کند و برای وضعیت‌های running و done مجاز نیست.

Queue tabs and pagination

The Queue controller separates the Hesabfa request queue and the Internal API request queue into two tabs. Filters and pagination are independent per tab. Compact pagination is displayed in a stable left-to-right order on both LTR and RTL back-office pages.

اصلاح هشدار صف در نسخه 2.3.20

در هشدار سراسری صف، فقط وضعیت‌های needs_attention و duplicate_check به‌عنوان نیازمند بررسی دستی محاسبه می‌شوند. وضعیت dead به معنی بسته یا کنار گذاشته‌شدن دستی رکورد است؛ بنابراین رکوردهای مرده در جدول و تاریخچه صف باقی می‌مانند، اما هشدار Queue attention required را فعال نگه نمی‌دارند. وضعیت retry_wait همچنان هشدار انتظار برای تلاش مجدد ایجاد می‌کند.

هشدار صف و آمار اصلاح‌شده لاگ‌ها در نسخه 2.3.19

اگر صف اصلی یا صف API داخلی شامل رکوردهای retry_wait، needs_attention یا duplicate_check باشد، در بالای صفحات مدیریت ماژول هشدار نمایش داده می‌شود. رکوردهای dead در تاریخچه صف باقی می‌مانند، اما هشدار سراسری را فعال نگه نمی‌دارند. آمار لاگ نیز فقط شدت‌های ۳ و ۴ را به‌عنوان خطا و شدت ۲ را به‌عنوان هشدار محاسبه می‌کند.
